# Engineering challenge notes

The proposal covers all 79 assigned rows. It keeps 41 Diamond, 21 Gold, 15 Silver and 2 Bronze. It does not change any row’s `class`. The tier changes follow consequence: exploitable access/privacy failures, lost enquiries/data and unsafe cutovers stay Diamond; repeatable user experience and release checks are Gold; telemetry, scanner scores, optional protocol support and specialist hardening are Silver/Bronze.

## Strongest counterexamples

- **Headers are controls with different scopes, not a blanket score.** SEC-02 bans every `Server` header, while HOST-16 correctly says a generic `Server` value alone is not a gap. OWASP calls `Server` not a security header and says removal or a non-informative value is enough. OWASP also says correct MIME type plus `nosniff` matters most where browsers render untrusted content. COOP can sever a window relationship used by OAuth popups; CSP and CORP need to match actual frames, assets and provider integrations. See [OWASP HTTP Headers](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html), [MDN COOP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cross-Origin-Opener-Policy), and [MDN frame-ancestors](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors).
- **CORS is not authentication or a general CSRF defense.** CORS controls browser access to responses. Direct API callers still need server authorization; cookie-authenticated state changes need risk-appropriate CSRF protection. OWASP notes SameSite has gaps for sibling subdomains and safe-method mutations, and explicitly allows narrow cross-origin integrations/webhooks with separate controls. See [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) and [OWASP REST Security](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html).
- **An origin allowlist is better than “zero third parties” as a hard invariant.** First-party by default is sound privacy posture. A necessary, owner-approved provider may still be valid if its data use, browser permissions, CSP/SRI and failure path are reviewed. SEC-04 must permit exactly those approved origins; SEC-12 still blocks unreviewed executable code.
- **Authentication records do not prove mailbox arrival.** Google currently distinguishes all senders (SPF or DKIM) from bulk senders (SPF, DKIM and DMARC), while recommending all three generally. Its one-click rule is limited to qualifying bulk promotional mail. The FTC confirms the 10-business-day opt-out deadline and that the mechanism must remain available for 30 days. DMARC policy must account for every authorized sender: current [RFC 9989](https://www.rfc-editor.org/rfc/rfc9989.html) recommends monitoring first and warns about `p=reject` interoperability. RFC 8461 testing mode reports policy failures while allowing delivery. None of these records substitutes for MAIL-06’s real inbox and reply-route check. See [Google sender guidelines](https://support.google.com/mail/answer/81126), [FTC CAN-SPAM guide](https://www.ftc.gov/business-guidance/resources/can-spam-act-compliance-guide-business), and [RFC 8461](https://www.rfc-editor.org/rfc/rfc8461.html).
- **Certificate renewal is not a universal cron.** [RFC 9773](https://www.rfc-editor.org/rfc/rfc9773.html) lets ACME servers provide a suggested renewal window, so fixed 60-day/two-thirds schedules and future lifetime forecasts should not be hardcoded. The actual gate is valid HTTPS plus a working renewal and failure path. TLS 1.0/1.1 are deprecated under [RFC 8996](https://www.rfc-editor.org/rfc/rfc8996.html), supporting the protocol floor in HOST-02.
- **Charset placement should follow the parsing standard.** The HTML Standard requires the encoding declaration early in the byte stream; “first element in head” is stricter than needed. See the [HTML Standard charset declaration requirements](https://html.spec.whatwg.org/multipage/semantics.html#charset).
- **Static brochure sites do not need server architecture by default.** SQL pools, authorization matrices, webhooks, health routes, error collectors and real-user analytics are conditional. Mark absent features N/A. A browser-facing contact form, however, still needs bounded input, abuse protection, privacy-safe handling and proven receipt.

The demotions preserve the dangerous controls in their proper rows: request/body bounds stay in BACK-04/BACK-17; injection, authorization, CSRF and cache isolation remain Diamond; webhook/payment idempotency remains in BACK-22/23; live enquiry delivery remains MAIL-06; DNS/mail continuity remains HOST-19/22; and privacy controls remain mandatory whenever analytics or persistent data is actually collected. HOST-14 retains Diamond for recoverable approved content and any mutable customer data, while its restore evidence now follows the data held. These are proposals only; no canonical checklist rows were edited.
