## 3. Extract, specify, assert

Pull real computed values off the live page: computed-style archetypes per page × viewport, pseudo-elements, CSS variables, `@font-face` rules, the authored stylesheet rules (media queries, keyframes, easings), the full type scale, the colour palette with exact values, spacing, radii, shadows, borders, grid and container widths, measured breakpoints, and a fingerprint of the stack and scroll library. Measure motion numerically: durations, easings, staggers, distances, lerp and inertia constants, parallax factors, clamp bounds, the scroll library's settings. Never read a value off a screenshot.

Then write `DESIGN.md` (contract §4) and `assertions.json`: an array of `{selector, prop, expected, layer}`, one entry per viewport × state × selector × property.

- `selector` is `"<viewport>|<state>|<css selector>"`. `prop` is a kebab-case CSS longhand (`padding-left`, never `padding`) or one of the pseudo-properties below.
- `layer: "rest"`: colour, background (gradients included; image `url(` values excepted), type metrics (font-size, weight, line-height, letter-spacing), padding, margin, gap, grid tracks, radius, border, box-shadow, backdrop-filter, display and flex or grid alignment, position and offsets, z-index, cursor, `max-width`, the `width`, `height` and `x-rect-*` of layout boxes (sections, containers, columns, media frames), and the final `transform` and `opacity` of each state. A pseudo-element's `content` string is copy, handled as a slot, never asserted. What depends on the content leaves this layer only through the swap probe (§6), never by judgment.
- `layer: "motion"`: `transition-*`, `animation-*`, `scroll-behavior`.
- `layer: "substituted"`: only `font-family` (when an open substitute is used) and values that contain `url(` (`background-image`, `mask-image`, `cursor`, `list-style-image`, `border-image-source`). The strict comparator fails any other prop labelled `substituted` and prints the substituted count per viewport, which the README reports. List every substituted value, with the original and clone values, in `WS/substitutions.json`.
- Pseudo-properties (the only non-CSS props allowed): `x-rect-top`, `x-rect-left`, `x-rect-width` and `x-rect-height` in px, and `x-line-count` (the number of lines: take the rects of each text node in the block with its own `Range.getClientRects()`, drop zero-width rects and merge rects that overlap vertically; one range over the whole block also returns element boxes, which overcount) and `x-line-starts` (the first word of each line joined by `/`), which are always `content`.
- `layer: "content"`: content-dependent entries, recorded for the original as slot budgets and never compared with it for equality: every `x-line-*` entry, and after the swap the entries the swap probe moves here (§6). In the reference build the clone gate (§5) holds the `x-line-count` of each slot within ±1 of the original's; the strict comparator skips and counts `content` entries, and fails any that is neither `x-line-*` nor listed as changed in `WS/gates/swap-probe.json`.
- Coverage: your assertion builder prints `elements covered: X/Y` and `states covered: X/Y`, where Y counts every rendered element of the original that has text, media, an icon or a painted background in every state of `STATES-MANIFEST.md`, each repeated child, SVG and pseudo-element included (not one archetype per role), and every one of them maps through `WS/selector-map.json`. Both must be 100%. Layout geometry (sizes, offsets, alignment) and the colour of every text node and icon are asserted from the first cycle; adding a new assertion family later restarts the cycle count.
- **Lock.** `WS/assertion-changes.md` starts with the initial SHA-256 of `assertions.json`. Every change appends the reason, the measurement file it came from and the new SHA-256, and rewrites `WS/gates/assertions.lock`. Regenerate assertions only from a new measurement of the original (the swap probe counts as one). Each change is its own commit in the `WS` repository. A brand shift (§6) never edits `assertions.json`: `WS/brand-map.json` is a separate file whose own SHA-256 is recorded in `assertions.lock`.

## 5. Prove the match

Everything in this section except the production gate, which audits the shipped build (§6), runs against the reference build (`WS/reference-app`, rule 4): the clone carrying the original's own content, so that any difference is a defect in the clone and not a difference in content. §6 then repeats the relevant gates on the shipped build.

**The comparator.** The contract names `assert-styles.mjs` as the gate, and you run it, but on its own it can pass a false match: it compares only the first number in any value that has units. Reproduced: a `padding` of `10px 60px` passes against an expected `10px 20px`, and a `box-shadow` with a different colour, offset and blur passes when its first number matches. Also reproduced: `opacity` 0 against 1, `transition-duration` 0.3s against 1.2s, `z-index` 10 against 11 and a line count of 3 against 4 all pass. So write `WS/tools/assert-strict.mjs`, which reads the same two JSON files plus each assertion's `layer` and compares token by token.

- Tolerances: `px` ±1, `em` and `rem` ±0.01, `%` ±0.5, `s` ±0.005, `ms` ±5, `deg` ±0.5, opacity and colour alpha ±0.01; in `matrix()` and `matrix3d()` the translation entries ±1 px and every other entry ±0.001. Colour channels, unitless numbers (`font-weight`, `z-index`), keywords and function names must match exactly, and a value with a different number of tokens fails. A selector or property missing from the clone's styles is a failure, never a skip. `substituted` and `content` entries are skipped and counted, subject to the allowlists in §3.
- Exit 0 only when `rest` and `motion` have zero failures.
- Smoke test before you use it, saved to `WS/gates/strict-smoke.txt`, with exactly these six cases: `transform-origin` `10px 20px` against `10px 60px` (must fail); `box-shadow` `rgba(0, 0, 0, 0.5) 0px 4px 12px 0px` against `rgba(0, 255, 255, 1) 0px 40px 90px 30px` (must fail); `opacity` `1` against `0` (must fail); `transition-duration` `0.3s` against `1.2s` (must fail); `width` `400px` against `400.9px` (must pass); a selector missing from the clone's styles (must fail). The upstream script passes the first four.

Run both comparators and save both outputs. The strict one is the gate.

**Clone gate** (on the reference build). Drive each state exactly as a user would (move the pointer, hover, click, scroll in steps, wait for transitions to end), read `getComputedStyle` for every asserted key into `clone-styles.json`, and run the comparators. Iterate the convergence loop until there are zero `rest` and `motion` failures and `npm run build` exits 0.

**Target validation (required).** Assertions are keyed by original selectors, and `WS/selector-map.json` maps each to a clone selector. Run the same reader against the live original, and against the reference build through the map, scored with the same assertions. Every mismatch means the spec recorded an authored value where the runtime computes something else (for example a JS-injected `cursor: none`, or an unscoped variable falling back to black). Correct the assertion to the runtime value (log it in `assertion-changes.md`), fix the clone to match, and re-run both. Final state: the clone has 0 failures and the original has 0 failures on the same `rest` and `motion` set (excluding states marked `state-changing on a live site`, and `content` entries). Record the URL, capture date, viewport, font-load state and interaction state with both runs. If the live site changes during your build, refresh the baseline and say so.

**Line-break parity.** In the reference build, for every text slot in `WS/slots.json` at every viewport and at 320 px wide, the clone's `x-line-count` is within ±1 of the original's, and `x-line-starts` shows where they differ; a larger gap is a fidelity failure (widths, type metrics or the font substitute are wrong), so fix the clone. The ±1 allowance does not excuse the `rest` entries a line difference moves (the box's height, the offsets below it): those still fail, so tune the substitute until the counts match. No text is clipped by an ancestor whose `overflow` is not `visible` unless the original clips it too, no two text slots overlap unless they do in the original, and the page has no horizontal scroll. Save `WS/gates/line-parity.json`.

**Motion gate.** Record every recorded motion sequence on both sites with the same in-page `requestAnimationFrame` recorder, started by the same dispatched trigger event. End values must be within the rest tolerances. Completion time, the first frame after which the value stays within tolerance of its end value, must be within ±50 ms. At each 16 ms step, `abs(clone - original) / max(abs(range), 1 unit)` must be at most 0.08, where range is end minus start of the original; a property with zero range is compared with the rest tolerances. For scroll-driven motion, progress-based effects are compared at the same section progress (§2) and per-pixel factors at the same scroll distance from the section's start, and must meet the rest tolerances. Anything you cannot measure numerically (shader output, for example) goes in a list of unmeasured items with a frame-strip comparison instead. Intro channels include the values at `DOMContentLoaded` and any hidden initialisation behind a loader, so a channel that starts differently is found before it is tuned. For each library the original uses, read its version and settings at runtime and compare them with yours.

**Production gate.** Write `WS/tools/prod-audit.mjs`. It runs every checklist row whose Verify column names a command or snippet, against the deployed build (§4, §6) served by `npm run start` with `SITE_ENV=production` unless the row says otherwise, at the four viewports (and in Chromium, WebKit and Firefox where a row says so), and writes `WS/gates/production.json` (row ID, status, measured value, evidence path) plus a readable `WS/gates/production.md`. It fails if `WS/checklist-map.md` or `production.md` lacks a line for any checklist row, by ID. A row whose Verify names another gate's output (EDGE-14, CNT-06, CNT-14, CNT-16, DEL-08) takes that gate's status and evidence path. It also runs the `BACK` rows against the local server when server code exists, and records every `-L` row as `AWAITING-DEPLOY`, implemented in `npm run audit:live` (§8), and every `-O` row as `OWNER-CONFIRM` until human evidence exists. Also produce the DEL-15 release record; machine observations and attestations remain distinct. Smoke test before use, saved to `WS/gates/prod-smoke.txt`: on ten deliberately broken fixtures it must fail the row each targets, listed in `prod-smoke.txt`: a server that answers 200 for a missing path (SEO-03), a page with no `lang` (TYP-05), an image without `width` and `height` (SPD-04), an uncompressed CSS file (SPD-07), a hashed asset without long cache headers (SPD-06), an Open Graph image that returns 404 (SEO-05), a secret-like literal in the source (SEC-06), a background image with no first-paint colour (TYP-13), a blocked image that blanks the page (EDGE-05) and a page whose copy is hidden with JavaScript off (EDGE-06). A predicate that cannot fail is not a check. Rows that need judgment (microcopy, composition) are filled in by hand in the same table. Run the same audit on the original for the baseline (§2) and print clone versus original for every numeric row. Record each `FIDELITY-EXCEPTION` in `WS/fidelity-exceptions.md` (row, the original's value, the cost of fixing it, what you did instead).

**Convergence loop** (contract §6). At most 10 cycles. Two consecutive cycles with no drop in failures, from cycle 2, end the loop as `STUCK`; reaching the cap is `CEILING`. Either one ends the loop, not the run: write `WS/escalation.md` with the remaining failures, record gate 1 as `FAIL` (`escalation.md` must also list every remaining visible defect from `WS/gates/visual-review.md`), and carry on with every later step; the polish pass is then `NOT_RUN`, because its baseline needs green gates. A build that will not compile is a defect to fix, never a reason to stop; if the loop ends with it broken, ship the last commit that builds and report the failure. Never present a failure as passing. Failure counts in the loop are the strict comparator's `rest` plus `motion` failures. Adding a new assertion family after cycle 1 restarts the cycle count.

**Eyeball pass** (after the convergence loop ends). Side-by-sides, original next to the reference build (both carry the original's content; compare design system, layout, spacing, colour, type and component states), at the recorded rest frames at all four viewports and every key state, plus frame strips of the intro, transitions and scroll reveals. Fix what the assertions cannot see: clipping, stacking, remounts, timing, line breaks. A long capture batch can catch a crossfade mid-transition, so re-shoot before you "fix". Save the clone's rest frames as PNGs in `WS/09-polish/rest` (reveals finished, `document.fonts.ready` resolved, the pointer never moved onto the page) as your visual record. §7 takes its own baseline later, on `app`'s fidelity build.

**State walk.** Write `WS/tools/state-walk.mjs`. It opens every state in your `interaction-map.json` (the menu and every overlay open, the footer, each hover, focus and pressed state, each language, and mobile navigation with JavaScript disabled) at `desktop`, `laptop`, `tablet`, `mobile` and a 320 px viewport, saves a screenshot per state, and checks on rendered pixels: every text node and icon has at least 4.5:1 contrast (3:1 for large text and icons) against the background sampled under it with the text hidden, so ink-on-ink cannot pass (the walk also runs on the original: a node no lower than the original's same node in the same state is a `FIDELITY-EXCEPTION`, EDGE-14, not a failure); every backdrop or overlay covers its intended area (non-zero, and the viewport for a full-screen backdrop); clicking outside a panel, pressing Escape and using the close control each dismiss it; no text is clipped or overlapping; every navigation destination is reachable with JavaScript disabled. It runs on the reference build in this section and again on the shipped build after the swap (§6). Save `WS/gates/state-walk.json`. Smoke test it against a fixture with dark text on a dark panel, a zero-height backdrop and a clipped button label: it must flag all three (`WS/gates/state-walk-smoke.txt`). When a smooth-scroll library is in use, `window.scrollY` may not describe the visual position and a bounded number of wheel events may not reach a section: reach sections with the keyboard (`End`, `Home`), the library's own `scrollTo` or by scrolling an element into view, and confirm the state with bounding boxes before trusting a screenshot's name.

## 6. The swap: the client's content goes in

Run this when §5's gates on the reference build and the repo's `07-polish.md` stage (or its `NOT_RUN`) have ended, whether they passed or are recorded as failed. From here `app` is what ships; the reference build is used only to re-check code you fix. Nothing in this section edits `assertions.json` except the swap probe's moves to `content` (step 3), each logged through the lock (§3).

**1. Write the content.** Apply the mapping and the content ladder (Inputs) to every slot in `WS/slots.json`: write `content/site.json`, process the media (§4), fetch stock where the ladder calls for it, draft copy where it allows, and keep the system copy. Run `WS/tools/validate-input.mjs` and record which rung filled each slot in `docs/CONTENT_GAPS.md` and `docs/CONTENT_NOTES.md`.

**2. Brand shift (on by default).** Skip it only when `design_shift` is `none`. Otherwise:
- `palette`: the original's colours (clustered, with their roles, from `DESIGN.md`) map to the brand's colours in `WS/brand-map.json`: one entry for every distinct colour in `assertions.json`, keyed by its computed sRGB channels (`r, g, b`) and mapped through its cluster (a colour that does not change maps to itself). Brand colours without roles are assigned by rank of luminance and chroma; colours the brand does not supply are derived as tints or shades of the brand's in OKLCH, converted to sRGB channels (§4), and that is recorded. With no brand colours at all, derive the palette from the original's: rotate the hue of every chromatic colour (chroma of 0.02 or more) by one fixed angle between 30° and 60° in OKLCH, the same angle everywhere so the relationships between colours hold, keep chroma, then set each rotated colour's lightness so its WCAG relative luminance equals the original colour's (contrast follows relative luminance, not OKLCH lightness), lowering chroma only as far as sRGB needs, take the direction (plus or minus) that keeps more chroma in total, record the signed angle, and leave neutrals as they are; if the original has no chromatic colour the palette stays the original's and that is logged. Every text and background pair keeps at least the contrast the original's pair has (1% is allowed for rounding to 8-bit channels, J), and at least 4.5:1 (3:1 for large text) where the original meets it; a colour for which any pair cannot keep that contrast maps to itself, so it stays the original's everywhere, and is logged. The map is applied in the brand token file and nowhere else, and gradients, shadows and overlays follow by token.
- `palette+type`: additionally, the display and body families are replaced by the brand's typefaces: the licensed files from `CLIENT_INPUT/fonts` (licence in `rights.md`), the brand face itself when it is open-licensed, or else the open-licensed face closest to it among about 30 measured candidates. With no brand typefaces, choose for each family the open-licensed face of the same classification (serif, sans, mono, display) that is not the original's family and is closest to it by the §4 measures among about 30 candidates (a commercial original's §4 substitute qualifies, and then that family stays as built), and apply the same width limit. A new face's cap-height-normalised text width must be within 8% (J) of the original face's, or that family is not shifted and the reason is logged. Type scale, spacing and line heights stay the original's, and a weight moves, by at most 100, only where the new face lacks the original's; fit the new face with `size-adjust` and the override descriptors.
- The locked assertions stay untouched. The shift lives in its own token file (`src/styles/brand.css`), which overrides the original's tokens and which `reference-build.mjs` empties. `WS/brand-map.json` also records, per shifted family, the new family name and any weight change. The strict comparator takes `--brand-map` and rewrites the expected values before comparing: the channels inside every `rgb()` and `rgba()` (alpha kept, nothing outside a colour function touched) and, for a selector whose expected `font-family` is a shifted family, its `font-family` and `font-weight`; it prints how many values it rewrote. An expected colour in another function (`oklch()`, `color(srgb ...)`) is converted to sRGB channels for the lookup and written back in its own function. What the tokens cannot reach (colours inside images, video and generated placeholders, `filter` functions, third-party defaults) is listed as unshifted in `WS/brand-map.json` and `docs/CONTENT_NOTES.md`. Geometry that a new face moves is measured by the swap probe, which carries the brand typefaces (step 3). Record the map, the contrast table and the before and after pairs in `WS/substitutions.json`, `docs/CONTENT_NOTES.md` and the README.

**3. Swap probe.** Load the original (context option `bypassCSP: true`) and, in the browser only (nothing is sent), make it carry what the shipped build carries: each text slot gets its `site.json` value (filling any per-line, per-word or per-character wrappers the way the original's split code does), each image or video slot a same-size neutral data-URL placeholder, each launch essential the clone adds (checklist rule 2) a copy of the original's nearest equivalent element in the same place, each section in `hidden_sections` removed, and, with `palette+type`, the shipped brand `@font-face` rules are injected as `data:` URLs under the original's family names. Run every viewport × state context separately and at 320 px wide, re-inject after every state change (the original's scripts may re-render), and confirm with bounding boxes that the state was reached and the injected text is present, then re-read every `rest` entry and every slot's `x-line-count`. Save both to `WS/gates/swap-probe.json` with the SHA-256 of the `site.json` it injected, which must equal the shipped one. An entry whose value moves beyond tolerance depends on the content: move it to `content`, logged in `assertion-changes.md` with the probe as its measurement. An entry whose element disappears under the probe stays in `rest`, except in a hidden section, whose entries move to `content`. Re-run the probe whenever `site.json` changes. From now on, run the comparator on the reference build with `--reference`, which scores the entries the probe moved as `rest` again, because there the content is the original's.

**4. Strict comparator on `app`.** Serve `app`'s fidelity build with `npm run start` and run the comparator with `--brand-map` when a brand shift applies: 0 failures on `rest` and `motion`, with the `substituted` and `content` counts printed. A failure that the reference build did not have is a swap defect (a hard-coded size, a clipped box, a colour outside the tokens): fix the app, never the assertion, then re-run the reference build to confirm it still passes. Repeat the motion gate on the fidelity build (where a motion value derives from content-dependent geometry, the original loaded with the swap probe's content is the other side) and the state walk on the deployed build.

**5. Copy-fit gate and swap parity.** With the shipped content in place, for every text slot in `WS/slots.json` at every viewport and at 320 px wide: the clone's `x-line-count` is within ±1 of the swap probe's for the same content (a larger gap is a fidelity failure: widths or type are wrong, so fix the clone; under `palette+type` the probe carries the same typefaces, step 3); the probe's count against the original's own is the copy-fit budget (a deviation beyond ±1 is a copy-fit note with a recommended length in `docs/CONTENT_NOTES.md`, not a failure); for every entry moved to `content`, when the clone's line count equals the probe's, the clone's value is within the rest tolerances of the probe's, so the clone reflows as the original does under the same content; no text is clipped by an ancestor whose `overflow` is not `visible`, no two text slots overlap unless they do in the probe, and the page has no horizontal scroll; text over images keeps 4.5:1 contrast (3:1 for large text), computed with the text hidden as the 5th-percentile contrast of the background pixels under its line boxes; every media slot holds a client file, a stock file or a marked placeholder. Where the client's copy overflows a box the design fixes in size, keep both the design and the copy: the slot is `FAIL`, with a recommended length in `docs/CONTENT_NOTES.md`, for the client to decide. Save `WS/gates/copy-fit.json`.

**6. Production loop.** Run `prod-audit.mjs` on the shipped build (`npm run start`, `SITE_ENV=production`). Fix every failing applicable `G` or `C` row in the app, in checklist order and invisibly first (checklist rule 2). Before the first batch, shoot the reference build's rest frames twice and mask the regions that differ, as §7 invariant 1 does. After each batch, rebuild both builds, re-run the audit, then re-run the strict comparator and the motion gate on the reference build (rebuild it with `reference-build.mjs`) and on `app`'s fidelity build, the state walk, and the reference build's rest frames: a change to the private fidelity build that adds a comparator or motion-gate failure is isolated from that build and recorded as a fidelity deviation; the required deployed safety fix is retained in `A11Y_FIXES` where an accessibility rule forced it. At most 3 cycles; an applicable `G` or `C` row that still fails stays `FAIL` and goes into `escalation.md`. Finish by doing the `R` rows or listing them, and bring `WS/checklist-map.md` up to date.

**7. Leak check.** Run the checks of gates 6 and 13 now, before the polish pass, and fix what they find: nothing of the original's text, images, video, fonts, logo, code or domain is in `app`, its build output or its git history. A leak in the history is removed by rewriting it (for example with `git filter-repo`, or by re-creating the repository from the clean tree), then `git reflog expire --expire=now --all && git gc --prune=now`, never by a later commit.

## 7. Final polish pass with the scroll-craft skill (additive only)

Run this after §5 and §6, on `app`'s fidelity build (flag off, §4), and before you write the final results into the README. It enhances what §1 to §6 built. It never removes, restyles or rebuilds any of it, and if nothing needs fixing it changes nothing.

The skill is at `<KIT_DIR>/skills/scroll-craft` (call it `SKILL_SRC`). Use it only to find and fix roughness in scroll feel, motion and interaction. The repo's own Stage 9 polish (`07-polish.md`) still runs first, as corrected in the Methodology. This pass comes after it, and may write under `WS/09-polish/scrollcraft` (call it `POLISH`) even though `07-polish.md` says to write nothing else.

Read from the skill's `references` folder: `verify.md` (what the harness reports, what it cannot tell you, and "The phone is a different machine"), the cue contract in `devices.md` (§2) and `approved-collection.md` §7. The Method below replaces Step 5. Do not run `workspace.mjs --ensure`, copy `engine`, load `scrollcraft.css` or edit `scrollcraft.js`. **Invariants** (checked and evidenced in the report, not promised):

The two sets must differ by 0 pixels; otherwise add only the differing regions to `POLISH/masks.json` and use that mask in every later diff. Masks may cover at most 5% of each frame and are listed in the README. Capture with infinite CSS animations paused at `currentTime` 0, scroll set to integer offsets with `scrollTo`, and the pointer never moved onto the page. Save the frames to `POLISH/shots/before/rest` and copy `<name>/app` (without `.git`, `node_modules` or build output) to `POLISH/source-before`. These, not the §5 frames, are the baseline.

After the pass, the same unedited assertions (the lock hash still matches) give zero `rest` and `motion` failures on `app`'s fidelity build and on a rebuilt reference build, the motion gate still passes with deviations no larger than before, the copy-fit gate and the production audit show no row worse than before, and the build is clean. 5. If no fix is kept, `<name>/app` (without `.git`, `node_modules` or build output) is byte-identical to `POLISH/source-before` and only the report remains.

**Method.**
1. Set up outside the app. In `POLISH` run `npm init -y && npm i playwright-core` (the harness resolves it from the working directory), and set `SCROLLCRAFT_HOME` to an absolute path inside `POLISH` so nothing lands in the app. Run `doctor.mjs` (in the `scripts` folder of `SKILL_SRC`) from `POLISH` and save the output. It needs installed Google Chrome (set `SCROLLCRAFT_CHROME` if it isn't found) and a full ffmpeg build for the contact sheet. Fix any `required` failure and the `Chrome` and `playwright-core` rows (doctor marks those `verify`, but the harness cannot run without them). A missing KIE key is fine.
2. Instrument without touching the app. The harness only walks pages that carry its hooks. Copy `shoot.mjs` into `POLISH` as `shoot-clone.mjs` (leave the skill's own copy alone) and add a `page.addInitScript` that stamps the following on `DOMContentLoaded` and re-stamps from a `MutationObserver` (the DOM does not exist when an init script first runs), using your clone's selectors from extraction:
   - `data-sc-act="flow"` on each section root; `pin`, `pan` or `scrub` instead on sections the original pins, pans or scrubs (`flow` sections get no dead-scroll check unless any element on the page carries `data-sc-verify-state`, in which case every pair of samples is checked).
   - `data-sc-copy` on text over media.
   - `data-sc-verify-state` on fixed stages, canvases and WebGL layers, set to a rounded signature of what actually paints, never raw scroll progress; `data-sc-verify-hold="true"` only during a genuine resolved hold. Put `data-sc-verify-state` only on layers whose painted state is scroll-driven in the original; a static fixed layer gets none. A dead-scroll report in a span where the original is also still is `inherited`.
   - the class `sc-ready` on `<html>` once the intro has ended and fonts have loaded (the harness times out after 15 seconds without it).
3. Serve the fidelity build with `npm run start`, never `file://`, and confirm the port is yours (ground rule 7).
4. Baseline run, from `POLISH`: `node shoot-clone.mjs --url <url> --width 1440 --height 900 --out shots/before/laptop`, then `--width 375 --height 667 --out shots/before/mobile`, then `--width 1440 --height 900 --reduced-motion --out shots/before/reduced`. Read every `sheet.png` and `report.json`.
5. The harness cannot judge smoothness, so smoothness defects are defined numerically. During a scripted wheel scroll of 100 px per 16 ms at `laptop`, a defect is any frame over 33 ms, any scroll-position step more than 2× the median step, or any element whose transform jumps more than 40 px between consecutive frames, on the clone but not on the original at the same section progress (§2). Nothing else counts as a smoothness defect. For each animated section, keep a strip of the clone and of the original at the same viewport and section progress as evidence.
6. Write `findings.md`: every harness finding (dead scroll, cues that never peak, contrast failures, console errors, failed requests, broken images), every keyboard, reduced-motion and touch problem, and every smoothness defect. **Allowed fixes.** Each must trace to a defect in `findings.md`.
- Scroll smoothing: move the clone's smooth-scroll settings toward the original's measured values from §3, never away from them, and never add a library the original does not use. Touch keeps native momentum. Keyboard, space, Page Down, anchor links (offset under a fixed nav) and scroll restoration keep working. No snapping or scroll-jacking the original doesn't do. Plain native scroll under `prefers-reduced-motion`.
- Dead scroll: only where the original shows motion in that span, reproduce the original's motion there. Never invent a cue, parallax or reveal, and never change heights.
- JS-driven motion that stutters or snaps (lerp, tweens, drag inertia, cursor follow, page transitions): retune easing and timing only toward the original's measured easing, duration and trajectory, so the motion-gate deviation shrinks, keeping start and end states. Copy reaches full opacity and does not re-hide on scroll-up wherever the original does the same. Never retune toward the skill's own taste rules.
- Reduced motion: fewer and gentler, not zero. Keep the opacity that carries meaning, drop position changes, keep all content reachable.
- Robustness: console errors, failed requests, broken images, focus landing on invisible controls, keyboard open and close of menus, and forms (no personal data in the URL, no false "sent" state).

Put new code in its own module (`src/polish`), switchable with `?polish=off` read once at boot, so one build serves both the before and after captures. Edit an existing file only when a defect cannot be fixed additively, and log the file and the reason.

**Loop and report.** After each batch of fixes: rebuild, re-run the harness (laptop, mobile, reduced) into `shots/after/{laptop,mobile,reduced}`, re-run the gates, re-shoot the rest frames, and re-measure heights and rects. Revert any batch that regresses any of them. At most 3 cycles; whatever remains is listed as open. Target: zero dead scroll, zero cues that never peak, zero contrast failures, and zero console errors and failed requests, apart from `inherited` items. Write `POLISH/polish-report.md` with the findings table and classes, a change table (defect, change, before and after evidence), the gate numbers before and after, the rest-frame diff result, open items, and what a real phone could show that headless Chrome cannot (`verify.md`, "The phone is a different machine"). If nothing needed fixing, the report says "No change required" and lists the checks that were run.
