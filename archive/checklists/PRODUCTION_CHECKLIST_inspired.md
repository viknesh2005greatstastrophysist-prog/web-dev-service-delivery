# Production-grade checklist for client sites designed as a close cousin of an award-style inspiration

Purpose: a client site is production grade when it is an original design that keeps the inspiration's grammar and ideas and differs from it in measured ways (section DST), carries only the client's own content, and equals or beats the inspiration on speed, accessibility, robustness, discoverability, security and launch readiness. Every row below except the owner-only `-O` rows is checkable by an unattended agent (Playwright, Lighthouse CLI, axe-core, curl, grep); a row whose Verify column says Review is filled by hand with saved evidence. Inspired edition: a human deploys the package, so live-only rows are checked afterwards by `npm run audit:live`, and owner-only rows are confirmed by the owner.

**Classes.** `G` = must pass. `R` = recommended, do unless it costs the design something you can name. `C` = conditional: applies only if the feature exists, otherwise record `N/A` with the reason. A `-L` suffix (for example `G-L`) marks a row that can only be checked on a live deployed URL, by `npm run audit:live -- <url>` after a human deploys. An `-O` suffix (for example `G-O`) marks an owner-only row (accounts, monitoring, backups, timed drills): neither the agent nor `audit:live` can check it, so it is listed in `docs/LAUNCH_CHECKLIST.md` with a concrete confirmation step and recorded `OWNER-CONFIRM`, never `PASS`.

**Statuses** for the audit table: `PASS`, `FAIL`, `N/A` (with reason), `AWAITING-DEPLOY` (live-only rows before the human deploys), `OWNER-CONFIRM` (owner-only rows), `NOT_RUN`. No `PASS` without saved evidence.

**Rules of application**
1. **Beat-or-match.** Run the same audit (Lighthouse mobile and desktop, axe, header check, 404 probe, console log, transfer size and request count) on the reference first, and save it as the baseline. On every numeric row your site must be equal or better (5% tolerance for run-to-run noise), and it must also meet the absolute threshold in the row wherever the reference meets it. Where the reference misses a threshold, your site must still be equal or better, and the row is logged. Numeric rows are: Lighthouse Performance score, LCP, CLS, TBT, transferred bytes, request count, JS bytes, the MOT-01 frame-time figures, the Accessibility and Best Practices scores, and the SEO score with the `is-crawlable` audit excluded (staging builds are `noindex` by design, SEO-02, and fail that audit). Compare LCP as LCP minus TTFB, so a site served from localhost and a remote reference are comparable.
2. **The design is yours, so the rows apply in full.** There are no fidelity exceptions: never copy a failure of the inspiration (low contrast, small targets, missing focus states, an intro that cannot be skipped), and design the accessible, fast, robust version from the start. Where a row and your design seem to conflict, change the design. The client's content (copy, images, logo, contact details) follows the client. Distance from the inspiration is a requirement of its own (section DST) and never a reason to weaken a row.
3. **Measure like Lighthouse does.** Mobile profile = Slow 4G (RTT 150 ms, 1.6 Mbps down, 750 Kbps up) and 4x CPU slowdown. Use the median of 3 runs. Lab numbers are a proxy: INP is a field metric, so use the longest event duration in a scripted interaction run as the lab proxy. Pin one Lighthouse version and use it for both sites (Lighthouse 13 removed some older audits).
4. Numbers marked (J) are judgment calls, not published standards. Everything else cites its basis.
5. **Deploy-ready, deployed by a human.** The agent never deploys, creates an account or handles a credential. Live-only rows (`-L`) are recorded `AWAITING-DEPLOY`, and each is implemented in `npm run audit:live -- <url>` together with the artifacts that make it pass on deploy (host header file, `404.html`, redirect rules, DNS records in `docs/DNS.md`, CI workflow, `docs/DEPLOY.md`). Never mark a live-only row `PASS` from localhost. After the human deploys, `audit:live` turns them into `PASS` or `FAIL`. Owner-only (`-O`) rows stay `OWNER-CONFIRM` until the owner ticks their confirmation in `docs/LAUNCH_CHECKLIST.md`.
6. **Backend rows.** A site with no form has no server code: record `BACK-00` as static and every other `BACK` and `MAIL` row as `N/A`. A site with a form ships one real contact endpoint (BACK-01), which makes every `BACK` row apply, and `MAIL` applies when the site sends email. Missing provider configuration yields an honest 503, never a fake success.
7. **Every `N/A` needs an absence predicate**, a machine-checked fact saved as evidence, for example `document.querySelectorAll('canvas').length === 0`, `typeof window.gsap === 'undefined'` or `!document.querySelector('form')`. Rows that name a feature (SPD-09, TYP-10, TYP-15, RSP-07, A11Y-07, A11Y-10 to A11Y-13, EDGE-07, MOT-03 to MOT-05, MOT-07, MOT-08, MOT-11) apply only when the predicate for that feature is false. Rows that name a client feature (CNT-10, I18N-01, LEG-04 to LEG-06, LEG-09, LEG-13, LEG-15) apply per `legal.md` and `brief.md`; record the predicate from those files, and if a file is missing assume the minimum (no accounts, payments, analytics or cookies). Predicates and feature detectors inspect your authored source (`src/`) or runtime behaviour, never minified bundle text or vendor library code: a library's drag or ScrollTrigger strings do not make a feature.
