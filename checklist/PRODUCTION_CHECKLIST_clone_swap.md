# Production-grade checklist for client sites cloned from an award-style design reference, with the client's content swapped in

Purpose: a client site is production grade when it reproduces the design reference's design system, layout and motion everywhere a visitor can see them, carries none of the reference's content (the client's own, or drafted, stock or placeholder content standing in for it, each labelled), and equals or beats the reference on speed, accessibility, robustness, discoverability, security and launch readiness, to a gold standard: each row keeps the published floor and, where a primary source or a derivation supports it, adds a stricter target (rule 9). Automation provides partial evidence. Visual judgment, real assistive technology, physical devices, rights, approvals and recovery require the named reviewer or owner. A snippet in Verify is a starting method, not proof of the whole requirement. This document defines a delivery standard; its existence does not certify any website. Clone-and-swap edition: the clone is proven against the reference with the reference's own content in a private reference build, then the client's content is swapped in; a human deploys the package, so live-only rows are checked afterwards by `npm run audit:live`, and owner-only rows are confirmed by the owner.

**Classes.** `G` = must pass. `R` = recommended, do unless it costs fidelity. `C` = conditional: applies only if the feature exists, otherwise record `N/A` with the reason. A `-L` suffix (for example `G-L`) marks a row that can only be checked on a live deployed URL, by `npm run audit:live -- <url>` after a human deploys. An `-O` suffix (for example `G-O`) marks an owner-only row (accounts, monitoring, backups, timed drills): neither the agent nor `audit:live` can check it, so it is listed in `docs/LAUNCH_CHECKLIST.md` with a concrete confirmation step and recorded `OWNER-CONFIRM` until a named human supplies dated evidence. Only then may the row become `PASS`; an agent must not invent the confirmation.

**Statuses** for the audit table: `PASS`, `FAIL`, `N/A` (with reason), `FIDELITY-EXCEPTION` (see rule 2), `AWAITING-DEPLOY` (live-only rows before the human deploys), `OWNER-CONFIRM` (owner-only rows), `NOT_RUN`, and `UNAVAILABLE` (only SPD-21 when field data is insufficient). No `PASS` without saved evidence. `FIDELITY-EXCEPTION` and `INHERITED` are not passing production results. See [release evidence contract](../docs/RELEASE_EVIDENCE.md).

**Rules of application**
1. **Comparable measurements.** Save the original baseline and final client build using the same pinned tools, browser versions, viewport, device scale, cache state, consent state and throttling. Record three cold-cache runs per route and profile, median and worst run. Compare scores, full LCP, CLS, TBT, transfer bytes, request count, JS bytes and motion timing. The 5% noise allowance is house policy (J), applies only to comparable baseline regressions, and never relaxes a pass threshold. Do not subtract TTFB from LCP: it removes part of the visitor experience and does not equalise networks or servers. Local-versus-remote figures are diagnostic, never a beat-or-match PASS; repeat against a deployed HTTPS build (SPD-20). Keep noindex staging SEO scores separate from production crawlability. Test final approved content, and record media substitutions that affect cost.
2. **Fidelity is measured separately from production safety.** Preserve the original in the private reference/fidelity build and retain its immutable measurements. The deployed build always enables `A11Y_FIXES=on`, regardless of geography. It must fix accessibility failures, broken primary actions, deceptive behaviour, privacy/security failures and loss of content, including when a visible change is necessary. Record the exact visible difference and reference evidence in `docs/FIDELITY_EXCEPTIONS.md`; never loosen the fidelity assertion or call the production defect a PASS because the original also has it. Apply invisible fixes first. The client content ladder, brand tokens and documented launch essentials remain permitted. An unresolved required production row blocks launch; recording its risk or accepting the reference look does not waive it. Never replace a verified safe build with the fidelity build through a client preference switch.
3. **Reproducible lab profiles.** Pin Lighthouse and the browser and save the effective settings from each report. Use its mobile and desktop presets, recording the network model, CPU slowdown, benchmarkIndex and any supported calibration method/version; apply the same settings to both targets. Simulated Lighthouse throttling and CDP applied throttling are different methods: name the method and never apply both at once. Convert Kbps to bytes per second when using CDP. Take the median of three runs and retain all raw reports. Record Event Timing interaction durations in a scripted flow as a lab diagnostic, never field INP. An unsupported API, failed control or empty interaction sample is `NOT_RUN`, never zero. SPD-21 covers real-user results.
4. Numbers marked (J), strict budgets, required tools and test matrices are house delivery policy, not universal web standards. Keep primary-source links and checked dates in the source register. Tool support and hosted service behaviour must be rechecked for the pinned version and selected host; historical review notes are not current verification.
5. **Finish work without claiming release.** Missing inputs never stop preparation of a reviewable package. Required local failures make the handover decision BLOCKED, not deploy-ready. Live-only rows are `AWAITING-DEPLOY` before deployment; owner-only rows are `OWNER-CONFIRM` until evidence exists. Neither is a production PASS. The human performs the approved cutover and runs `audit:live`; record the actual release revision, artifact hash, build id, URL, timestamp and tester. Live checks plus required owner confirmations close the launch decision. Use the executable evidence validator in DEL-15; its success validates records, not the truth of a screenshot or legal judgment.
6. **Applicability follows the real system.** BACK-00 inventories all server code, including form, CMS, analytics, error-reporting, account and webhook endpoints. No form does not imply no backend. Evaluate each BACK row against that inventory; a C row is required when its feature exists. MAIL sending controls apply when mail is sent; receiving-domain and migration controls also apply to existing business email even if the new site has no form. An unconfigured contact endpoint may return an honest 503 during preparation but cannot pass production delivery (MAIL-06).
7. **No unsupported N/A.** Only conditional C rows, recommended R rows with a documented absence, and retired LEG-07 may be N/A. Convert feature-dependent requirements to C explicitly. Save the absence predicate and its observed result across all routes, states and relevant server/provider configuration. A single empty DOM query, absent input file, no third-party browser request or unknown configuration cannot prove absence. Missing facts are NOT_RUN or OWNER-CONFIRM, with the disabled feature and unresolved decision listed. Client/legal applicability needs the actual data flow and owner/counsel review; never infer that legal duties disappear because legal.md is missing. Inspect authored source and runtime behaviour, not vendor strings.
8. **Every row is traced.** `WS/checklist-map.md` and `production.md` list every stable row ID. The machine-readable release record follows `docs/RELEASE_EVIDENCE.md`: exact checklist SHA-256, release revision/artifact/build identity, full route and state coverage, tester/time, measured result, evidence file hashes, and a reason/next action for every unresolved item. No omitted or duplicate rows, unknown statuses or stale evidence. Grouped evidence must identify the covered checks. Keep secrets and personal data out of public reports; retain redacted evidence privately. Rebuilds, content, configuration and deployment changes invalidate affected results.
9. **Gold is evidence, not a score label.** SPD-13 and other stricter targets are explicit house budgets (J); they do not prove a percentile ranking, business conversion or WCAG conformance. All applicable G and C rows must pass for launch. A FIDELITY-EXCEPTION preserves the measured shortfall and blocks a required production row until fixed. Recommended R misses need an owner, reason and review date; they prevent a gold decision but need not prevent launch. Field data may be UNAVAILABLE only for SPD-21; report that limit without inventing a field pass. Required floors and exact pass thresholds are never relaxed by baseline noise, reference defects or owner acceptance.
10. **Friction, not compulsion.** The experience rows remove friction between a visitor and the reference's own calls to action: speed, clarity, feedback, recovery. They never add anything whose purpose is to manufacture engagement or pressure (infinite feeds, autoplay with sound, countdowns, scarcity claims, nagging prompts, confirm-shaming, pre-ticked consent), and UXF-07 checks for them.

| SPD-03 | The LCP resource is discoverable in initial HTML or preload, is not lazy-loaded, and receives appropriate priority when it is an image. Text LCP needs no fetchpriority attribute. | SPD-04 | Every `<img>` and `<video>` has `width` and `height` (or CSS `aspect-ratio`); images below the fold use `loading="lazy"` and `decoding="async"`, unless that makes them pop in during a fast scripted scroll where the original's do not. | Playwright: for each img, attributes present; CLS attributable to images = 0 | G |

| SPD-10 | Video: poster image, `muted playsinline`, `preload="metadata"` or none when off-screen; nothing downloads before it is needed; bytes ≤ original's. | Playwright network log before scroll | R |
| SPD-11 | Test back/forward restoration in supported engines with an eligible control and real navigation. Investigate browser not-restored reasons. | SPD-12 | Optional Speculation Rules for safe same-origin navigation only, feature-detected and tested in supported browsers. | SPD-13 | House gold lab budgets (J), median of three runs per scoped route on each pinned profile: mobile FCP ≤ 1.2 s, LCP ≤ 1.8 s, TBT ≤ 100 ms, CLS ≤ 0.02, Speed Index ≤ 2.0 s; desktop FCP ≤ 0.6 s, LCP ≤ 0.8 s, TBT ≤ 50 ms, CLS ≤ 0.02, Speed Index ≤ 0.95 s. These are project budgets, not proof of field INP or a top-decile website. A missed required target is FAIL; retain fidelity diagnostics separately. | Raw reports, effective profiles, tested routes, three-run median and worst run; interaction trace | G |
| SPD-14 | The origin adds no delay. | SPD-16 | Compressed landing HTML target ≤ 14 KiB (J). | SPD-17 | House transfer budgets (J): resources required before LCP, excluding the LCP image itself, total at most 170 KB compressed; all JavaScript requested before load is at most 170 KB compressed. Neither exceeds a comparable original baseline. These are delivery budgets, not a population ranking. Record each library and its cost; a reference library or fidelity exception does not waive a required miss (rule 9). | Pinned Lighthouse/network trace and initiator chain; identify actual render dependencies, not every early request as critical. Save byte totals, units, exclusions and the comparable baseline; unsupported report fields must fail the control rather than return zero | G |
| SPD-18 | House critical-path budget: at most one render-blocking stylesheet ≤ 30 KiB compressed, no CSS @import chains, and no avoidable parser-blocking executable script. JSON-LD, import maps and speculation rules are data blocks, not deferred executable scripts. Discover or preload critical LCP images and fonts deliberately. | Inspect executable script types separately from data blocks; saved waterfall and Lighthouse insights | G |
| SPD-19 | Text assets are precompressed at build (Brotli at its top quality and gzip at level 9) and served with the matching `Content-Encoding`, so the server never spends request time compressing; Brotli is preferred when offered. | Build output lists `.br` and `.gz` siblings; `curl -sI -H 'Accept-Encoding: br'` shows `content-encoding: br` | R |
| SPD-20 | Repeat SPD-01 and SPD-13 on the actual deployed HTTPS URL with the final content and matched settings. Record cache state, location, redirect chain and causes of regressions. One extra round trip is not a universal local-to-live tolerance. No API key is required when using locally installed Lighthouse. | audit:live stores all reports, compares raw values, and checks the actual deployed build id | G-L |
| SPD-21 | Real-user Core Web Vitals: p75 LCP ≤ 2.5 s, INP ≤ 200 ms and CLS ≤ 0.1, separately by mobile/desktop. Record collection window, source, URL versus origin scope and sample eligibility. With insufficient data record UNAVAILABLE, name the review owner/date, and make no field pass claim. | CrUX or privacy-reviewed RUM report; never substitute Lighthouse or maximum scripted event duration | R-L |
