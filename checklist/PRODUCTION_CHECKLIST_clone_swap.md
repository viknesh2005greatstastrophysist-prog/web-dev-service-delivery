# Production-grade checklist for client sites cloned from an award-style design reference, with the client's content swapped in

<!-- priority-policy: risk-v2 -->

Purpose: a reusable requirements catalogue for client websites. Start with the [tiered operating checklist](TIERS.md): Diamond protects essential journeys, accessibility, security, privacy, legal obligations and safe release; Gold covers smooth delivery and experience; Silver covers useful enhancements; Bronze retains specialist polish, reference comparisons and legacy bookkeeping. These are agency priorities, not external certifications. Every stable row remains traceable. The Tier column controls release priority; the requirement and Verify cells retain the detailed acceptance check. Reference fidelity remains a separate contracted deliverable and never excuses a safety failure. Automation provides partial evidence; a well-formed record does not certify the website.

The [video lessons add-on](VIDEO_LESSONS_ADDON.md) maps the nine supplied clips to this catalogue, explains evidence and rejects unsupported shortcuts. It adds no separate pass status.

**Applicability and timing.** The legacy Class column is retained for compatibility: `G` means always applicable, `C` means conditional on the feature or legal applicability, and `R` means an enhancement whose absence must be evidenced if marked N/A. `G` no longer means Gold or a launch blocker; the separate Tier column determines that. `-L` means final-domain verification after controlled cutover; `-O` means named human evidence, not an engineering task the agent may simply decline. Missing evidence is not N/A. Handover permits explicitly pending live/owner records and never authorizes launch. The row register in [tiers.json](tiers.json) records purpose and timing. Timing metadata never waives an applicable Diamond check.

**Statuses** for the audit table: `PASS`, `FAIL`, `N/A` (with reason), `FIDELITY-EXCEPTION` (see rule 2), `AWAITING-DEPLOY` (live-only rows before the human deploys), `OWNER-CONFIRM` (owner-only rows), `NOT_RUN`, and `UNAVAILABLE` (only SPD-21 when field data is insufficient). No `PASS` without saved evidence. `FIDELITY-EXCEPTION` and `INHERITED` are not passing production results. See [release evidence contract](../docs/RELEASE_EVIDENCE.md).

**Rules of application**
1. **Comparable measurements.** Save the original baseline and final client build using the same pinned tools, browser versions, viewport, device scale, cache state, consent state and throttling. Record three cold-cache runs per route and profile, median and worst run. Compare scores, full LCP, CLS, TBT, transfer bytes, request count, JS bytes and motion timing. The 5% noise allowance is house policy (J), applies only to comparable baseline regressions, and never relaxes a pass threshold. Do not subtract TTFB from LCP: it removes part of the visitor experience and does not equalise networks or servers. Local-versus-remote figures are diagnostic, never a beat-or-match PASS; repeat against a deployed HTTPS build (SPD-20). Keep noindex staging SEO scores separate from production crawlability. Test final approved content, and record media substitutions that affect cost.
2. **Fidelity is measured separately from production safety.** Preserve the original in the private reference/fidelity build and retain its immutable measurements. The deployed artifact must pass applicable accessibility checks in every geography. If separate fidelity and accessibility build modes exist, production always selects the accessible mode. It must fix accessibility failures, broken primary actions, deceptive behaviour, privacy/security failures and loss of content, including when a visible change is necessary. Record the exact visible difference and reference evidence in `docs/FIDELITY_EXCEPTIONS.md`; never loosen the fidelity assertion or call the production defect a PASS because the original also has it. Apply invisible fixes first. The client content ladder, brand tokens and documented launch essentials remain permitted. An unresolved Diamond production row blocks launch; recording its risk or accepting the reference look does not waive it. Never replace a verified safe build with the fidelity build through a client preference switch.
3. **Reproducible lab profiles.** Pin Lighthouse and the browser and save the effective settings from each report. Use its mobile and desktop presets, recording the network model, CPU slowdown, benchmarkIndex and any supported calibration method/version; apply the same settings to both targets. Simulated Lighthouse throttling and CDP applied throttling are different methods: name the method and never apply both at once. Convert Kbps to bytes per second when using CDP. Take the median of three runs and retain all raw reports. Record Event Timing interaction durations in a scripted flow as a lab diagnostic, never field INP. An unsupported API, failed control or empty interaction sample is `NOT_RUN`, never zero. SPD-21 covers real-user results.
4. Numbers marked (J), strict budgets, required tools and test matrices are house delivery policy, not universal web standards. Keep primary-source links and checked dates in the source register. Tool support and hosted service behaviour must be rechecked for the pinned version and selected host; historical review notes are not current verification.
5. **Finish work without claiming release.** Missing inputs never stop preparation of a reviewable package. Diamond local failures make the handover decision BLOCKED, not deploy-ready. Live-only rows are `AWAITING-DEPLOY` before deployment; owner-only rows are `OWNER-CONFIRM` until evidence exists. Neither is a production PASS. The human performs the approved cutover and runs `audit:live`; record the actual release revision, artifact hash, build id, URL, timestamp and tester. Diamond live checks plus Diamond owner confirmations close the launch decision. Use the executable evidence validator in DEL-15; its success validates records, not the truth of a screenshot or legal judgment.
6. **Applicability follows the real system.** BACK-00 inventories all server code, including form, CMS, analytics, error-reporting, account and webhook endpoints. No form does not imply no backend. Evaluate each BACK row against that inventory; a C row is applicable when its feature exists and its Tier determines the release gate. MAIL sending controls apply when mail is sent; receiving-domain and migration controls also apply to existing business email even if the new site has no form. An unconfigured contact endpoint may return an honest 503 during preparation but cannot pass production delivery (MAIL-06).
7. **No unsupported N/A.** Only conditional C rows, enhancement R rows with a documented absence, and retired LEG-07 may be N/A. Convert feature-dependent requirements to C explicitly. Save the absence predicate and its observed result across all routes, states and relevant server/provider configuration. A single empty DOM query, absent input file, no third-party browser request or unknown configuration cannot prove absence. Missing facts are NOT_RUN or OWNER-CONFIRM, with the disabled feature and unresolved decision listed. Client/legal applicability needs the actual data flow and owner/counsel review; never infer that legal duties disappear because legal.md is missing. Inspect authored source and runtime behaviour, not vendor strings.
8. **Every row is traced.** `WS/checklist-map.md` and `production.md` list every stable row ID. The machine-readable release record follows `docs/RELEASE_EVIDENCE.md`: exact checklist SHA-256, release revision/artifact/build identity, full route and state coverage, tester/time, measured result, evidence file hashes, and a reason/next action for every unresolved item. No omitted or duplicate rows, unknown statuses or stale evidence. Grouped evidence must identify the covered checks. Keep secrets and personal data out of public reports; retain redacted evidence privately. Rebuilds, content, configuration and deployment changes invalidate affected results.
9. **Diamond cannot be waived.** All applicable Diamond rows must PASS before launch evidence can be complete. No owner risk acceptance, aesthetic preference, missing provider access, lower tier target or aggregate score can override them. Conditional N/A needs an observed absence predicate and evidence; a required feature cannot be removed just to pass the gate. Gold completion requires Diamond plus Gold; Silver scope adds Silver; full-catalogue completion adds Bronze. Nonblocking misses still need a reason, owner, next action and review date. Future field results, timed reviews and recurring drills remain honestly pending at their assigned tier. SPD-21 alone may be UNAVAILABLE for insufficient field data; it never becomes a field PASS. Read TIERS.md before applying a tier to a mixed requirement. Any newly discovered critical risk or applicable legal duty is Diamond even if the catalogue omits it: record and resolve it before release.
10. **Friction, not compulsion.** The experience rows remove friction between a visitor and the reference's own calls to action: speed, clarity, feedback, recovery. They never add anything whose purpose is to manufacture engagement or pressure (infinite feeds, autoplay with sound, countdowns, scarcity claims, nagging prompts, confirm-shaming, pre-ticked consent), and UXF-07 checks for them.

## Priority policy (risk-v2)

Use [RELEASE_STANDARD.md](RELEASE_STANDARD.md) as the short operating view and [TIERS.md](TIERS.md) for the complete priority register. Diamond protects essential access and journeys, personal data, applicable legal duties, truthful content and safe release. Gold measures user-facing quality. Silver holds useful optional improvements. Bronze holds specialist/reference work and legacy traceability. These are agency priorities, not third-party certifications.

For each requirement, ask what actual failure it prevents, when that failure can occur, whether another control already covers it, and whether its exact tool or number is necessary. Reference fidelity, a convenient implementation and a universal safety requirement are different claims. The row's reviewed outcome and applicability govern production decisions. Rules about matching the original apply only to scoped reference-comparison work; they do not add undeclared Diamond or Gold gates. A stricter contracted target remains required through `release.required_rows`.

Repeated checks may share a single evidence bundle with explicit row and state coverage. No requirement is passed by its tier changing. Keep the old checklist snapshot and results; assess the new criterion against suitable evidence and rerun affected checks. The 275 stable IDs are an audit trail, not 275 independent test sessions.
