# Production-grade checklist for client sites cloned from an award-style design reference, with the client's content swapped in

Purpose: a client site is production grade when it reproduces the design reference's design system, layout and motion everywhere a visitor can see them, carries none of the reference's content (the client's own, or drafted, stock or placeholder content standing in for it, each labelled), and equals or beats the reference on speed, accessibility, robustness, discoverability, security and launch readiness, to a gold standard: each row keeps the published floor and, where a primary source or a derivation supports it, adds a stricter target (rule 9). Every row below except the owner-only `-O` rows is checkable by an unattended agent (Playwright, Lighthouse CLI, axe-core, curl, grep); a row whose Verify column says Review is filled by hand with saved evidence. Clone-and-swap edition: the clone is proven against the reference with the reference's own content in a private reference build, then the client's content is swapped in; a human deploys the package, so live-only rows are checked afterwards by `npm run audit:live`, and owner-only rows are confirmed by the owner.

**Classes.** `G` = must pass. `R` = recommended, do unless it costs fidelity. `C` = conditional: applies only if the feature exists, otherwise record `N/A` with the reason. A `-L` suffix (for example `G-L`) marks a row that can only be checked on a live deployed URL, by `npm run audit:live -- <url>` after a human deploys. An `-O` suffix (for example `G-O`) marks an owner-only row (accounts, monitoring, backups, timed drills): neither the agent nor `audit:live` can check it, so it is listed in `docs/LAUNCH_CHECKLIST.md` with a concrete confirmation step and recorded `OWNER-CONFIRM`, never `PASS`.

**Statuses** for the audit table: `PASS`, `FAIL`, `N/A` (with reason), `FIDELITY-EXCEPTION` (see rule 2), `AWAITING-DEPLOY` (live-only rows before the human deploys), `OWNER-CONFIRM` (owner-only rows), `NOT_RUN`. No `PASS` without saved evidence.

**Rules of application**
1. **Beat-or-match.** Run the same audit (Lighthouse mobile and desktop, axe, header check, 404 probe, console log, transfer size and request count) on the original first, and save it as the baseline. On every numeric row the clone must be equal or better (5% tolerance for run-to-run noise), and it must also meet the absolute threshold in the row wherever the original meets it. Where the original misses a threshold, the clone must still be equal or better, and the row is logged; a published floor (rule 9) that the clone still misses stays `FAIL`. Numeric rows are: Lighthouse Performance score, LCP, CLS, TBT, transferred bytes, request count, JS bytes, the MOT-01 frame-time figures, the Accessibility and Best Practices scores, and the SEO score with the `is-crawlable` audit excluded (staging builds are `noindex` by design, SEO-02, and fail that audit). Compare LCP as LCP minus TTFB, so a clone served from localhost and a remote original are comparable. The gold targets of rule 9 apply on top: the clone must meet them even where the original does not. Measure the clone with its shipped content, and say in the README where placeholder or stock media makes a number easier or harder than the original's.
2. **Design fidelity wins.** No production item may change the reference's design system, layout, motion or behaviour that a visitor can see or feel at the four viewports, in any recorded state, motion sequence, intro or interaction, whether or not an assertion covers it. That includes colour, type, spacing, cursor, focus appearance at rest, intro replay behaviour, scroll feel, image loading during scroll, and every asserted value. The client's content (copy, images, video, logo, contact details, and the `drafted`, `stock` or placeholder content standing in for it) is not part of the design reference and follows the content ladder, the brand shift of the prompt's §6 (on by default; colours and typefaces, changed only by token) is the only permitted change to the design system, and only these launch essentials the reference lacks are allowed, built from the reference's own components and styles: legal footer links and the pages they open (privacy notice, accessibility statement, imprint, terms, and a credits page when a stock licence or provider asks for credit), a consent banner, form success and error messages, a language switcher for a multilingual client, and the scrim of CNT-07. Solve items invisibly first (semantics, ARIA, meta, headers, loading strategy, fallbacks, `@supports` fallbacks). If only a visible or felt design change would fix an item (for example a low-contrast colour the reference uses, or an intro that always replays), keep the reference's behaviour, mark the row `FIDELITY-EXCEPTION`, and record the item, the reference's behaviour, the cost of fixing it, the legal or usability risk for the client and what you did instead, in `docs/FIDELITY_EXCEPTIONS.md`. Also ship each accessibility-driven fix behind the `A11Y_FIXES` build flag: off in the fidelity build, which the fidelity gates measure, and on in the deployed build for a US-facing client (or one to whom LEG-12 says an accessibility law applies), so the choice is a one-line change that needs no development work (DEL-08). Elsewhere in this checklist the shipped build is the deployed build, except for the fidelity gates (the prompt's §4).
3. **Measure like Lighthouse does.** Mobile profile = Slow 4G (RTT 150 ms, 1.6 Mbps down, 750 Kbps up) and 4x CPU slowdown. Desktop profile = Lighthouse's desktop preset (RTT 40 ms, 10 Mbps, no CPU slowdown). Use the median of 3 runs. Calibrate the CPU: the default 4x assumes a host in Lighthouse's high-end desktop bracket (`benchmarkIndex` 1,500 to 2,000, Lighthouse throttling guide), and a faster laptop at 4x behaves like a high-end phone, not the mid-tier phone the profile stands for. Record each report's `benchmarkIndex` and pass `--throttling.cpuSlowdownMultiplier` with the value of Lighthouse's CPU slowdown calculator (3 + (index - 1300) / 233 for an index of 1,300 or more, 2 + (index - 800) / 500 from 800, to one decimal); every row that says 4x CPU uses that multiplier, in Playwright through CDP `Emulation.setCPUThrottlingRate`. A row that throttles the network in Playwright uses Lighthouse's request-level equivalent of Slow 4G (CDP `Network.emulateNetworkConditions` with 562.5 ms latency, 1,474.6 Kbps down and 675 Kbps up: RTT × 3.75 and throughput × 0.9), never a bare 150 ms. Lab numbers are a proxy: INP is a field metric, so use the longest event duration in a scripted interaction run as the lab proxy. Pin one Lighthouse version and use it for both sites (Lighthouse 13 removed some older audits).
4. Numbers marked (J) are judgment calls, not published standards. Everything else cites its basis.
5. **Deploy-ready, deployed by a human.** The agent never deploys, creates an account or handles a credential. Live-only rows (`-L`) are recorded `AWAITING-DEPLOY`, and each is implemented in `npm run audit:live -- <url>` together with the artifacts that make it pass on deploy (host header file, `404.html`, redirect rules, DNS records in `docs/DNS.md`, CI workflow, `docs/DEPLOY.md`). Never mark a live-only row `PASS` from localhost. After the human deploys, `audit:live` turns them into `PASS` or `FAIL`. Owner-only (`-O`) rows stay `OWNER-CONFIRM` until the owner ticks their confirmation in `docs/LAUNCH_CHECKLIST.md`.
6. **Backend rows.** A site with no form has no server code: record `BACK-00` as static and every other `BACK` and `MAIL` row as `N/A`. A site with a form ships one real contact endpoint (BACK-01), which makes every `BACK` row apply, and `MAIL` applies when the site sends email. Missing provider configuration yields an honest 503, never a fake success.
7. **Every `N/A` needs an absence predicate**, a machine-checked fact saved as evidence, for example `document.querySelectorAll('canvas').length === 0`, `typeof window.gsap === 'undefined'` or `!document.querySelector('form')`. Rows that name a feature (SPD-09, SPD-12, TYP-10, TYP-15, RSP-07, RSP-09, A11Y-07, A11Y-10 to A11Y-13, A11Y-17, A11Y-19, A11Y-20, EDGE-07, MOT-03 to MOT-05, MOT-07, MOT-08, MOT-11) apply only when the predicate for that feature is false. Rows that name a client feature (CNT-10, I18N-01 to I18N-04, UXF-04, UXF-05, MAIL-04, LEG-04 to LEG-06, LEG-09, LEG-13, LEG-15) apply per `legal.md` and `brief.md`, and CNT-16 per `brand.md`; record the predicate from those files, and if a file is missing assume the minimum (no accounts, payments, analytics or cookies). LEG-07, a superseded placeholder row, is the one `N/A` recorded without a predicate. Predicates and feature detectors inspect your authored source (`src/`) or runtime behaviour, never minified bundle text or vendor library code: a library's drag or ScrollTrigger strings do not make a feature.
8. **Every row is traced.** `WS/checklist-map.md` (prompt §4) lists every row of this checklist by ID with the file or module that meets it, its `N/A` predicate, its `FIDELITY-EXCEPTION`, or the `audit:live` check or `docs/LAUNCH_CHECKLIST.md` step that covers it, and `production.md` has a line for every row. A row that is in neither is a failure of the audit, not a pass.
9. **Gold standard.** Each speed, interaction and experience row (SPD, UXF, MOT, EDGE-15) states a published floor (the "good" threshold) and, where one exists, a gold target: a stricter figure taken from a primary source or derived from one (for example the value that scores 0.98 on Lighthouse's own curve, SPD-13), at or beyond the top tenth of the 2025 HTTP Archive population where that is measured, and marked (J) where it is judgment. `G` rows must meet the gold target. A row may miss it only with a `FIDELITY-EXCEPTION` that records the measured value, the cost of reaching it and the reason (the reference's own construction, such as a full-screen video or WebGL hero, or a visible change the fix would need). The published floor is never waived: one that the shipped build misses is `FAIL`, even where the reference misses it too (rule 1 still requires the clone to be equal or better, and the README says the miss is the reference's), and the design is still not changed to pass it (rule 2). A floor that is itself judgment (J), such as MOT-01's, is a `FIDELITY-EXCEPTION` where the reference misses it too and the clone is equal or better. Accessibility thresholds keep rule 2's path: a `FIDELITY-EXCEPTION` in the fidelity build, met by its `A11Y_FIXES` fix in a deployed `build:a11y` build (DEL-08). Gold targets are measured on the shipped build with its shipped content: say in the README where placeholder or stock media makes one easier or harder.
10. **Friction, not compulsion.** The experience rows remove friction between a visitor and the reference's own calls to action: speed, clarity, feedback, recovery. They never add anything whose purpose is to manufacture engagement or pressure (infinite feeds, autoplay with sound, countdowns, scarcity claims, nagging prompts, confirm-shaming, pre-ticked consent), and UXF-07 checks for them.
